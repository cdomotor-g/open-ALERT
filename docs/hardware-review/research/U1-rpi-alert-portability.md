## 1. The conclusions that should change a decision

1. **The agent is already not tied to a Pi.** It is plain JavaScript with no npm packages ([agent/package.json:1-17](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/package.json#L1-L17)), and it runs unchanged on x86-64: 247 of 247 tests pass on Ubuntu 24.04 with Node 22, with Ubuntu's own Node 18.19.1, and from the signed release tarball. The Pi-only parts are few and each one falls back quietly (section 2).
2. **"A privileged Docker container" is not needed.** The earlier Mallow recipe ([open-ALERT site/trial.html:150-166](https://github.com/cdomotor-g/open-ALERT/blob/c467016117c6e0304cc9e5a24cff138f6fb6a763/site/trial.html#L150-L166)) runs the agent as root with `--privileged --network host`, from an unsigned copy of the `main` branch. I ran the *signed* release in a Debian 13 container as an ordinary user with every capability dropped, no-new-privileges and a read-only root, and it started and served its dashboard. What it really needs is read/write on the USB device files of the sticks — not tested here, because this machine has no USB stick (sections 8b and 9).
3. **What ties RPi ALERT to a Pi is the installer and the image, not the agent.** `os/install.sh` wants Debian's `apt`, expects Raspberry Pi OS and always installs things an enterprise will not accept (a password-less sudo account, an hourly key-fetch timer, a 64 MB cap on the whole system journal). A separate, thin "platform layer" can skip the installer and consume the signed tarball as it is (section 8).
4. **A web proxy is not honoured as shipped; a private certificate authority usually is.** With `HTTPS_PROXY` set, the agent's own uplink code fails to reach Flood-Net (it never asks the proxy). This can be fixed with no change to RPi ALERT: Node 22.21 or newer with `NODE_USE_ENV_PROXY=1`, or on Debian 12/13 and Ubuntu 24.04 a three-line start-up file that uses the `undici` package the distribution already installs — both tested. Debian's and Ubuntu's own `nodejs` trust the operating system's certificate store, so a private authority added the normal way just works; Node from nodejs.org does not, and needs `NODE_EXTRA_CA_CERTS` (section 6.4).
5. **As shipped, its defaults are those of an unattended Pi on a hill, not of a box on a government network.** Dashboard on every network interface over plain HTTP, readable in part without a login; its own Wi-Fi hotspot after three minutes without a network; Flood-Net administrators able to change settings, reboot it and install updates; reboots and network restarts by itself. Every one of these has an existing setting — the list is in section 6 — but four things have none and need small changes in RPi ALERT itself: which address the dashboard listens on, which host names it answers to, HTTPS, and a log line for each login attempt (section 8c).
6. **Releases are signed and the check works.** v0.23.1's source tarball verified against the pinned Ed25519 key with the project's script and, independently, with OpenSSL. The SD-card images are not signed (a checksum only), which does not matter off a Pi: only the tarball is needed (section 5).
7. **Pick the base operating system by its packages.** Debian 13 and Ubuntu 24.04 have a new enough Node and an `rtl-sdr` that already knows the RTL-SDR Blog V4. On Debian 12 the installer compiles the stick driver from the newest, unpinned source on GitHub at install time; on Ubuntu 22.04 Node is too old and the installer stops (section 2, rows 19–20).
8. **A speed data point.** The agent's own bench, run here inside the simulator, put one channel in a 1.44 MHz window at 6 % of one core of this 2.1 GHz Xeon; the repository's figure for a Pi 4 is 31 %. That is about five times a Pi 4 per core — one measurement on a shared virtual machine, so treat it as a rough guide (section 4).

### 5.4 The precise steps for a third-party installer

1. **Get the public key once, from somewhere you trust, and keep it.** It is `os/release-signing-key.pem` in the repository. Check its fingerprint against the one in `docs/release-signing.md` (and, better, against a copy the owner gives you by another route):
   ```sh
   node -e 'const c=require("crypto"),k=c.createPublicKey(require("fs").readFileSync("release-signing-key.pem"));
     console.log("SHA256:"+c.createHash("sha256").update(k.export({type:"spki",format:"der"})).digest("base64").replace(/=+$/,""))'
   # expect SHA256:fOdKIOUguw9edBdaecgkcSoJhXprGHvbNr1ddEVXOXI
   ```
2. **Download the two files** (into an empty folder):
   ```sh
   tag=v0.23.1
   curl -fsSLO https://github.com/cdomotor-g/RPi_ALERT/releases/download/$tag/rpi-alert-$tag-src.tar.gz
   curl -fsSLO https://github.com/cdomotor-g/RPi_ALERT/releases/download/$tag/rpi-alert-$tag-src.tar.gz.sig
   ```
   Here: SHA-256 `de01ee53…1e8cc85` for the tarball, the same digest GitHub's API reports for the asset.
3. **Verify — either way gives the same answer:**
   ```sh
   # the project's own 41-line script (Node only)
   node verify-release.js release-signing-key.pem rpi-alert-$tag-src.tar.gz.sig rpi-alert-$tag-src.tar.gz && echo verified
   # or with OpenSSL 3 alone, no project code at all
   openssl pkeyutl -verify -pubin -inkey release-signing-key.pem -rawin \
     -in rpi-alert-$tag-src.tar.gz -sigfile rpi-alert-$tag-src.tar.gz.sig
   ```
   Here: the script exited 0; OpenSSL 3.0.13 printed "Signature Verified Successfully"; a copy with one byte added was refused (exit 1).
4. **Check the version inside matches the tag** (the updater's own second check): `tar -xzOf rpi-alert-$tag-src.tar.gz rpi-alert-$tag/agent/package.json | grep '"version"'` → `0.23.1`.
5. **Unpack and install.** Either run its `os/install.sh` as root on Raspberry Pi OS or Debian, or — for a platform layer — copy only `agent/bin`, `agent/lib`, `agent/vendor`, `agent/web` and `agent/package.json` to `/opt/rpi-alert` (what the installer itself copies: [os/install.sh:155-173](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/os/install.sh#L155-L173)) and supply your own unit file.
6. **Optional, and worth it for an approval:** run the tests that came inside the verified tarball: `cd rpi-alert-$tag/agent && node --test test/*.test.js` (needs `socat` and `sshd` for three of them). Here: 247 of 247.

### 6.4 A web proxy and a private certificate authority

The agent makes its HTTPS calls with Node's built-in `fetch` and nothing else: [agent/lib/meganet.js:42](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/lib/meganet.js#L42), [agent/lib/stations.js:117](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/lib/stations.js#L117), [agent/lib/access.js:277-282](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/lib/access.js#L277-L282). There is no proxy setting and no certificate setting anywhere in the code (I searched for `proxy`, `NODE_EXTRA_CA`, `rejectUnauthorized` and `ca:`: no matches that are settings). The updater and the outage probe use `curl`, which honours `https_proxy` and the operating system's certificates by itself.

I tested with the agent's own uplink code (`agent/lib/meganet.js`, `reach()` and `rpc()`), a pretend Flood-Net with a certificate from a private authority, and a proxy that was the only way to reach it. Full output: `(working folder, not kept)/U1-evidence/proxy-ca-tests.txt` and `(working folder, not kept)/U1-evidence/container-proxy-ca-tests.txt`.

What follows:

- **Proxy.** Not honoured as shipped. Honoured, with no change to RPi ALERT, by either (i) Node 22.21 or newer and `NODE_USE_ENV_PROXY=1` in the unit's environment — Node's documentation: added in v22.21.0, "Active development" (<https://nodejs.org/docs/latest-v22.x/api/cli.html#node_use_env_proxy1>); Ubuntu 26.04 LTS packages Node 22.22.1 and Debian's next release Node 24 (package pages above); or (ii) on Debian 12/13 and Ubuntu 24.04, the three-line start-up file (`(working folder, not kept)/U1-evidence/preload-proxy.js`). Either belongs in a platform layer.
- **Private authority.** Debian's and Ubuntu's `nodejs` use the operating system's certificate store (tested: Ubuntu 18.19.1, Debian 13 20.19.2), so `update-ca-certificates` is all it takes — and the installer installs exactly that Node ([os/install.sh:95](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/os/install.sh#L95)). A Node from nodejs.org, NodeSource or a container image built on one does not; it needs `NODE_EXTRA_CA_CERTS`, or `--use-system-ca` (it worked on the Node 22.23 tested here; Node's documentation dates the option from 22.15).
- **The outage probe does not know about proxies.** If Flood-Net stops answering on a proxy-only network, the direct probes to 1.1.1.1 and the others fail too, the agent concludes "no network" or "a dead link", restarts NetworkManager after 15 minutes and — in the default `full` mode, if it reached Flood-Net in the last week — reboots the computer after 45 ([agent/lib/keeper.js:256-270](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/lib/keeper.js#L256-L270); [agent/lib/keeper.js:290-305](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/lib/keeper.js#L290-L305); [agent/lib/keeper.js:307-320](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/lib/keeper.js#L307-L320)). Set `self_recovery = off` behind a proxy.
- **Units do not inherit a proxy from `/etc/environment`** (from memory): the variables have to be set in a drop-in for `rpi-alert.service`, and for the updater and key-fetch units if they are used at all.

### 8b. An unprivileged container

**Done here, with no change to RPi ALERT** (`(working folder, not kept)/U1-evidence/Dockerfile.unprivileged-test`; `(working folder, not kept)/U1-evidence/container-run.txt`):

- Image: `debian:trixie-slim` + `nodejs` (20.19.2) + `rtl-sdr` (2.0.2) + `ca-certificates` + `curl`; the release tarball and its signature copied in and **verified during the build**, then `agent/{bin,lib,vendor,web,package.json}` copied to `/opt/rpi-alert`; a user with id 990; `ENV RPI_ALERT_PRIV=/nonexistent RPI_ALERT_ASSUME_CLOCK=1`. 290 MB.
- Run: `docker run --cap-drop ALL --security-opt no-new-privileges --read-only --tmpfs /tmp -v …:/etc/rpi-alert -v …:/var/lib/rpi-alert -p 127.0.0.1:18081:80 …`
- Result: user 990, capability sets all zero, `NoNewPrivs: 1`, the default seccomp filter on, root read-only; the dashboard answered HTTP 200 through the published port; `/api/config` without a login → 401 (a caller through a published port is not "local"); 23 MB of memory idle with no receivers. It could take port 80 without any capability because Docker allows that inside a container.

**So, the list of changes that belong in RPi ALERT itself, in order of worth:**

1. `web.bind` — the address the dashboard listens on (one argument to `listen`).
2. `web.hosts` — extra accepted host names; and a "behind a proxy" switch that decides whether loopback callers are trusted.
3. A log line for each dashboard login, failed and successful.
4. An option to require a login for everything.
5. Do not name `wlan0`.
6. The clock check: treat "systemd is not running" as "no systemd".
7. Installer options (or a second, minimal installer) that leave out the `alert` account, the key-fetch timer, the journal cap and Avahi; pin or drop the `rtl-sdr-blog` build.
8. Optional: a built-in proxy setting, and a "health only, no inventory" check-in.

Items 1 to 4 are a few dozen lines in one file ([agent/lib/web/server.js:1-491](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/agent/lib/web/server.js#L1-L491)) and each can default to today's behaviour, as the project's own release rule asks ([CLAUDE.md:18](https://github.com/cdomotor-g/RPi_ALERT/blob/37fee8bc3a15a4b6b624bd4ae6ae299610300aae/CLAUDE.md#L18)).

**Everything else can live in a platform layer that takes the signed tarball unchanged:** its own unit file (no `sudo`, full hardening, the proxy and certificate environment), a settings preset (`hotspot = off`, `remote_management = report` or `off`, `self_recovery = off`, `kiosk = off`), the udev rule and the driver block list, log forwarding, the firewall, and the organisation's own accounts, updates and patching.
